= Sync settings

The Sync settings screen lets you choose how (and whether) repSwim synchronises your training data with a remote backend, inspect the current state of the outbound mutation queue, and trigger a manual sync when needed.
It also houses the stopwatch display-style preference.

== Reaching this page

The screen is registered at the `/settings/sync` route.
It is reachable from the main Settings destination, which is available in the bottom navigation bar (or the navigation rail on wider layouts) as defined in `adaptive_shell.dart`.

== Offline-first behaviour

repSwim stores all data locally in SQLite.
Every session, lap record, profile, template, race time, and personal best is written to the on-device database the moment you create or edit it.
The app is fully usable with no network connection at any time.

NOTE: There is currently no live remote backend.
Sync is entirely optional.
When the sync mode is set to *Manual* or *Auto*, mutations are placed on a local queue ready to be sent to a future server-side service.
Until that service is connected, tapping *Sync now* will have no visible effect — the queue will accumulate items that remain pending.

== Common actions

=== Choosing a sync mode

A segmented button at the top of the screen offers three modes:

[cols="1,3", options="header"]
|===
| Mode | Behaviour

| Local
| All mutations are kept on-device only.
  Nothing is ever placed on the outbound queue.
  This is the default.

| Manual
| Mutations are queued as you make changes.
  The queue is only flushed when you tap *Sync now* explicitly.

| Auto
| Mutations are queued as you make changes.
  The app will attempt to flush the queue automatically when conditions allow.
|===

The selected mode is persisted in app settings and restored on next launch.

=== Triggering a manual sync

The *Sync now* button at the bottom of the queue-status section submits all pending queue items to the backend in one batch.
The button is enabled only when a backend client is configured and the current mode is not *Local*.
In the current release no backend client can be connected, so the button stays disabled and the status card reads _"No backend configured"_ regardless of the chosen mode.

After a successful sync attempt, the queue summary is refreshed automatically.

=== Changing the stopwatch display style

A dropdown near the bottom of the screen sets the visual theme of the stopwatch timer display.
The available styles are described in xref:stopwatch.adoc[Stopwatch].
The selected style is persisted in app settings.

== Queue status

The *Queue Status* section displays a row of chips, one for each state in the outbound mutation lifecycle:

[cols="1,3", options="header"]
|===
| Chip | Meaning

| Pending
| Mutations that have been recorded locally and are waiting to be sent.

| Processing
| Mutations currently being submitted in an active sync attempt.

| Failed
| Mutations that were rejected by the backend, or that could not be delivered due to a network error.

| Complete
| Mutations that have been accepted by the backend.

| Total
| The sum of all four states above.
|===

Each chip shows a count for the active profile.
The counts update automatically when the screen loads, and are refreshed after each *Sync now* attempt.

== Expected behaviour

=== What happens during a sync

When *Sync now* is triggered, `SyncService` fetches all `pending` items for the current profile from the local queue and submits them to the backend in a single call.
For each item the backend returns an accepted or rejected result:

* *Accepted* — the item is marked `complete` in the local queue.
* *Rejected* — the item is marked `failed` and the rejection reason is stored against the queue record.
* *No result returned* — the item is marked `failed` with the message _"Missing sync result"_.

A pull phase follows the push to retrieve any server-side changes; this phase is a placeholder and does not yet apply any data locally.

=== Failure handling

If the network call itself throws an exception, every pending item that was part of the batch is immediately marked `failed` in the local queue and the error detail is stored on each record.
The exception is then re-thrown.

When a queue item cannot be enqueued at all (for example if the database write fails), a dismissible warning card appears at the top of the screen with a warning icon and the failure message.
Tapping the *×* button on that card dismisses it for the current session.

Failed items remain in the queue with their stored error detail.
They are included in the *Failed* count shown in the Queue Status chips.
Tapping *Sync now* again will re-attempt only `pending` items; failed items must be retried by a future retry mechanism not yet implemented.

NOTE: Because there is no live backend, all sync attempts will result in items being marked `failed` until a backend client is wired up.
This is expected behaviour and does not affect local data integrity.
